# LedgerLine database design

Run `schema.sql` against a MySQL 8.0.16+ server to create the `ledgerline` database and its seven tables. It provisions the required `LL-CLEARING-USD` system account (not sample transaction data). Run `money-movement-migration.sql` once on a database created from the earlier schema; it enables the external-clearing account type and provisions that account. Run `idempotency-outcomes-migration.sql` once on an existing database to store replayable business failures. MySQL 8.0.16 or newer is specified because the schema uses enforced `CHECK` constraints.

## Tables and relationships

1. **`users`** stores login identity, password hashes, global role (`ADMIN`, `ACCOUNT_HOLDER`, or `AUDITOR`), token revocation version, account status, and creation time. Username and email are independently unique. Store only a one-way password hash, never a plaintext password.
2. **`accounts`** stores an account's owner, unique account number, type, ISO currency code, current `DECIMAL(19,4)` balance, status, and optimistic-lock version. `owner_user_id` is the authoritative ownership relationship; the owner has full access without needing a duplicate permission row. `EXTERNAL_CLEARING` is an unowned system account used as the balancing counter-account for external deposits and withdrawals; its balance is a signed net clearing position, not a spendable customer balance. Customer accounts cannot have negative balances. The balance is a transactional cached balance and must be changed in the same database transaction as its ledger entries.
3. **`account_permissions`** grants a different user a unique role on an account: `ACCOUNT_ADMIN`, `TRANSACT`, or `VIEW`. A user can have one permission per account. The optional `granted_by_user_id` records who granted it. Account owners are defined by `accounts.owner_user_id`.
4. **`transactions`** records the initiating user, optional source/destination accounts, transaction type and status, positive `DECIMAL(19,4)` amount, currency, description, and creation/posting timestamps. A transaction cannot reference the same source and destination. The application must enforce the account-side requirements for each transaction type.
5. **`ledger_entries`** contains positive debit or credit lines for a transaction and account. A transfer is represented by at least one debit and one credit whose totals match in the same currency. Enforce balanced entries and post them atomically with the transaction and account balance changes; MySQL row constraints cannot enforce a sum across entries.
6. **`idempotency_records`** stores a key scoped to its user, a SHA-256 request hash (64 hexadecimal characters), processing status, resulting transaction or replayable business-failure details, and optional expiry. `(user_id, idempotency_key)` is unique. The key is ASCII case-sensitive in the MySQL schema. Reusing a key with a different request hash is rejected. The request claim and financial operation commit in the same transaction, so the record cannot report success for a rolled-back operation. Expected insufficient-balance and inactive-account outcomes are stored as `FAILED` and replay the original conflict; unexpected database failures roll back the claim. The application currently leaves `expires_at` unset; clients must use a fresh key for every new operation.
7. **`audit_logs`** records the actor, action, affected entity type/id, optional JSON details, and occurrence time. `entity_type`/`entity_id` are intentionally polymorphic and therefore do not use a foreign key. Keep audit records append-only and avoid sensitive credentials or secrets in `details`.

## Integrity and posting rules

Money uses fixed-point `DECIMAL(19,4)` in both account balances and transaction/ledger amounts; use Java `BigDecimal`, never floating-point types. Currency is stored on both accounts and transactions; the application must reject mismatches unless an explicit FX design is added.

Account balance updates, transaction status changes to `POSTED`, insertion of balanced ledger entries, and completion of the idempotency record must happen atomically. Deposit/withdrawal services acquire pessimistic write locks on the customer and clearing account rows in ascending account-ID order before validating the available customer balance. Transfers lock both customer accounts in the same order. This serializes competing balance changes and avoids lost updates; the account `version` remains an additional optimistic-lock guard. The database unique index on the user/key pair serializes same-key retries across application instances; Java synchronization is not used.

Ledger entries are immutable after insertion. `LedgerEntryEntity` rejects JPA update and delete lifecycle events; application services should only insert entries, and corrections should be represented by new reversing transactions and entries. The database account used by the application should not be granted direct update/delete rights on posted ledger rows if database-enforced immutability is required.

The read-only account statement endpoint joins each ledger posting to its transaction and initiator, orders by posting time, and computes balances from the full account history before applying optional date/type filters. This keeps filtered rows' running balances accurate. Successful transfers have a matching debit and credit for the same amount; refused attempts remain in `audit_logs`, not in the ledger.

The SQL script is the explicit schema reference. The current development profile has Hibernate `ddl-auto=update`; use that only for local development. For shared or production deployments, apply reviewed schema migrations and disable Hibernate schema mutation.

## MySQL concurrency integration tests

`MySqlMoneyConcurrencyIntegrationTest` runs against an isolated, pre-created MySQL 8+ test database (not H2). Set `LEDGERLINE_MYSQL_TEST_URL`, `LEDGERLINE_MYSQL_TEST_USERNAME`, and `LEDGERLINE_MYSQL_TEST_PASSWORD`, then run `mvn -Dtest=MySqlMoneyConcurrencyIntegrationTest test` from `ledgerline-backend`. The URL must point to a dedicated empty test database: the test uses Hibernate `create-drop` and will create and drop its tables.

The suite launches concurrent requests on separate threads and checks same-key replay, competing withdrawals of `800.0000` and `700.0000` against `1000.0000`, account balances, ledger rows, transactions, idempotency records, refused-attempt auditing, and rollback after a database write failure. The regular H2 test suite is useful for fast coverage but is not a substitute for these InnoDB tests.
