# LedgerLine threat model

Scope: the current Node.js/Express backend, Mongoose models, MongoDB replica-set transaction boundary, and React client. Verification references the real HTTP integration tests in `ledgerline-backend/test/ledgerline.integration.test.js`; run them with `npm test` from the backend directory.

| Threat | Mitigation | Verification tests | Accepted residual risks |
|---|---|---|---|
| Double spending / lost updates | A money posting updates the account balance, posted transaction, balanced debit/credit ledger entries, and idempotency outcome in one MongoDB transaction. Writes to a shared account conflict and transaction retries re-read the balance. Customer balances are validated nonnegative; decimal arithmetic uses Decimal.js/Decimal128. | `two simultaneous withdrawals cannot overdraw an account`, `two simultaneous transfers preserve balances and ledger consistency`, `money conservation holds across a deposit`, and `each money movement records equal debit and credit entries`; checks persisted balances and ledger rows. | The test replica set has one member and does not model failover/network partitions. Production must use a supported multi-member replica set, backups, monitoring, and tested restore procedures. Clearing-account balances represent a settlement position and require operational reconciliation. |
| Duplicate requests / retries | A unique `(userId, idempotencyKey)` index and SHA-256 hash of normalized operation details arbitrate retries. The idempotency row commits in the same transaction as the money posting. Exact retries replay the saved response; different payloads conflict. | `duplicate transfer requests with the same key post only once`, `reusing an idempotency key with changed request details conflicts`, and `failed posting rolls back transaction, ledger, idempotency, and account updates`. | Keys have no expiry and may accumulate indefinitely. Key secrecy is not an authorization control: authenticated users can make new operations with new keys. Clients must retain the original key for a retry and use a new key for a new operation. |
| Concurrent withdrawals | Each operation reads and writes the account inside a database transaction; MongoDB write-conflict retry causes the later request to evaluate the committed balance rather than silently overwrite it. Insufficient attempts create a refusal audit record and no financial posting. | `two simultaneous withdrawals cannot overdraw an account` launches parallel HTTP requests and checks exactly one post, one conflict, nonnegative persisted balance, and ledger/transaction counts. `scripts/demo-concurrency.js` provides an interactive evaluation check. | Under high contention, MongoDB can exhaust transaction retries and return an error; clients should retry with the same idempotency key. A single-process in-memory lock is deliberately not relied upon. |
| Unauthorized account access | JWT subject and token version are checked against the database on every authenticated request. Account owner/permission checks are performed server-side. Admin and auditor roles are explicit; public registration always assigns `ACCOUNT_HOLDER`. | `users cannot access accounts they do not have permission to view`, `admin, auditor, and account-holder permissions are enforced`, `admin account changes are authorized and audited`, and `registration and login keep public users in the account-holder role`. | Stolen valid bearer tokens remain usable until expiry/logout; use HTTPS, short token lifetimes, protect browser storage, rotate secrets, and promptly revoke users. Account-permission administration is not currently exposed as an API. |
| Ledger tampering | The API has no ledger update/delete route. Mongoose ledger fields are immutable and schema hooks reject document saves, query mutation/deletion, and bulk writes. Corrections require a new reversing posting. | `ledger entries cannot be modified through application APIs` verifies unsupported HTTP mutation paths and Mongoose update/delete guards. Auditor endpoints are GET-only and role-gated. | Mongoose hooks do not protect against privileged direct database writes, shell access, or a compromised database administrator. Production database credentials should have least privilege; use independent backups/exports and external audit monitoring for stronger tamper evidence. |
| Transaction rollback / partial posting | Every financial write is inside `session.withTransaction`; unsupported standalone MongoDB is rejected and there is no non-transactional fallback. The idempotency claim rolls back together with a failed posting. | `failed posting rolls back transaction, ledger, idempotency, and account updates` triggers a balance-range failure after transaction/ledger work begins, then verifies that none of those writes persisted. | Failures after commit but before the HTTP response are inherently ambiguous to the client; retrying with the same key resolves the outcome. Infrastructure and backup recovery still require operational testing. |
| Deadlocks / write conflicts | Related account documents are saved in deterministic ObjectId order. MongoDB transaction write conflicts are retried by the driver; the whole callback contains database operations only. | `two simultaneous withdrawals cannot overdraw an account` and `two simultaneous transfers preserve balances and ledger consistency` exercise parallel requests and assert final database state. | MongoDB does not provide application-level row locks through these queries; extreme contention can cause bounded retries/aborts and temporary availability errors. There is no fairness guarantee between competing requests. |
| Idempotency-key misuse | Keys are printable ASCII, 1–128 chars, user-scoped, unique in MongoDB, and bound to a hash of the normalized operation type, account identifiers, amount, and description. Same key with changed details returns `409`. | `reusing an idempotency key with changed request details conflicts`; concurrent duplicate test verifies a single persisted transaction and identical replay response. | A caller can intentionally use many different keys to submit many valid operations. Rate limiting and abuse detection belong at the deployment/API gateway layer and are not implemented in the app. Retained keys have no automatic cleanup. |

## Deployment boundary

The Compose stack is intended for local evaluation only: its single-node MongoDB replica set has no database authentication and is bound to the local machine. Do not expose it to the internet or use it for production financial data. For production, use a managed authenticated TLS MongoDB replica set, inject `MONGO_URI` and `JWT_SECRET` through a secret manager, expose only HTTPS through a reverse proxy, and define backup, monitoring, access-review, and incident-response procedures.
